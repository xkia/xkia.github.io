项目协作规范 ​

这份文档是 CoveVeranda 的长期协作规范，适用于人工开发者和各类代码助手。仓库只使用 AGENTS.md 作为自动发现入口，不维护厂商专属规则文件。

项目范围 ​

CoveVeranda 是个人 macOS 开发环境仓库，主要包含：

  • lume/：Lume 自治数字助理，使用 PDM 管理，包含多平台消息接入、LLM provider、技能系统、插件系统、Web 控制台和本地知识库。
  • python/：独立 Python 工具集合，使用 PDM 管理。
  • docs/：VitePress 文档站。
  • shell/：macOS、终端和系统自动化脚本。
  • docker/、bin/：容器配置和可执行工具。

协作流程 ​

默认交付流程：

text
Ask -> Spec -> Build -> Verify -> Deliver
1
  • 需求不清楚时先澄清，不把猜测写进实现。
  • 非平凡改动要先沉淀可检查的计划或 spec。全仓通用内容优先放在 docs/，Lume 专属内容放在 lume/docs/。
  • 实现前先读现有代码和相关文档，遵循当前目录的工具链、命名和结构。
  • 交付前运行最窄但有意义的验证，并说明哪些验证没有运行。

文档放置 ​

长期有效的项目知识使用普通文档路径维护：

内容推荐位置

厂商专属入口不提交；统一迁移到 AGENTS.md 或普通文档

不要把长期维护规则写成单次会话记录，也不要为不同工具维护多份互相发散的说明。模型名称、LLM provider、API 适配等属于产品事实时可以保留，不需要为了“通用化”改写。

通用开发规则 ​

  • 保持改动聚焦在当前请求范围内，不做顺手重构。
  • 不覆盖用户未提交的改动；遇到相关冲突时先理解现状再处理。
  • 配置使用 TOML 文件和既有配置加载链路，不新增 .env 作为项目约定。
  • Lume 相关代码和文档变更限制在 lume/ 内，除非需要更新全仓入口或根文档。
  • 临时文件、运行产物和调试输出不要混入源码目录。Lume 运行时临时文件使用 lume/workspace/。
  • 新增脚本、工具或文档时优先复用现有目录结构和命名风格。

验证要求 ​

  • 文档结构或链接调整后，优先运行 npm run docs:build。
  • Lume 代码变更至少运行相关单测；跨核心链路变更运行 python3 -m unittest discover tests。
  • Python 工具变更优先在 python/ 下运行对应脚本或模块测试。
  • 无法运行的验证要在交付说明中写明原因。
